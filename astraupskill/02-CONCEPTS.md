# 2. Contracts and business rejection

Treat the quote flow as three contracts with different meanings. A valid request returns a `HiringQuoteDto`. An expected business rejection returns a failed application `Result<T>`, becomes HTTP 400 ProblemDetails, and should remain a visible error in the browser. An infrastructure failure, such as a refused `fetch`, rejects the promise and should offer retry. These outcomes must not collapse into one generic “success with a number” path.

The transport edge is untrusted even though the TypeScript type says `HiringQuoteRequest`. In [`HiringQuoteCalculator.cs`](../src/PeblClone.Application/Workforce/HiringQuoteCalculator.cs), `request` can be null; country and currency can contain whitespace or the wrong length; currency must also be alphabetic; and JSON can encode an integer outside the named `EmploymentType` enum. The calculator therefore uses `Trim().ToUpperInvariant()`, checks two and three characters, applies `character is < 'A' or > 'Z'`, and calls `Enum.IsDefined`. It rejects compensation at or below zero and above the demo ceiling. TypeScript unions guide a friendly caller, but they cannot protect a direct HTTP client or an old deployed browser.

Shape validation precedes the profile lookup. Once the normalized country is known, `SingleOrDefault` finds the profile. An unknown country produces a controlled “not currently supported” message. A known country can still reject an engagement: Japan does not allow contractor management in the demo profile. That is a business rule, not a malformed request. The calculator chooses synthetic rates and fees only after these gates. The `Result<T>` return makes an expected rejection explicit without using exceptions for ordinary user input.

The API helper in [`workforceApi.ts`](../src/PeblClone.Web/src/services/workforceApi.ts) preserves that distinction. For a non-OK response it reads the body, prefers ProblemDetails `detail`, then `title`, then raw text, and finally a status fallback when the body is empty. It throws. `createQuote` returns that promise directly. The dashboard’s `getDashboard` catch is a separate product decision and labels its mock data; copying that catch into quote creation would create unsupported numbers.

The currency example deserves care. A direct request with `" eur "` returns `Currency == "EUR"`, but compensation and all totals stay in the submitted numeric unit. There is no rate table, conversion date, payroll provider, or legal calculation. The browser uses USD because its form hardcodes it. A reviewer should call this a synthetic estimate with a normalized currency label.


## Sidebar: overflow and rounding are not the same lesson

Two arithmetic facts about C# are worth memorising here, because the calculator depends on both.

**Overflow.** For the integer types (`int`, `long`, `short`, ...) the default context is `unchecked`: `int.MaxValue + 1` silently wraps around to `int.MinValue` and your total is negative with no exception. You opt into detection with `checked(a + b)` (or project-wide with `<CheckForOverflowUnderflow>true</CheckForOverflowUnderflow>`). For `decimal` the rule is the opposite and the keyword is irrelevant: `decimal` **always** throws `OverflowException` when a result cannot be represented, in a `checked` or an `unchecked` context alike. `double`/`float` do neither — they quietly produce `Infinity`. So `checked` around a `decimal` sum is at best a comment and at worst a false reassurance; what actually protects the caller is the `try`/`catch` that converts the throw into `Result<T>.Failure`, plus the compensation ceiling that stops anything near the limit from arriving in the first place.

**Rounding.** `Math.Round(x, 2)` in .NET rounds *to even* ("banker's rounding") by default: `21.105` becomes `21.10`, not `21.11`. That is a defensible statistical choice and the wrong one for a customer-facing price, where people expect a half to round up and where an invoice that disagrees with the quote by a cent is a support ticket. The calculator therefore passes `MidpointRounding.AwayFromZero` explicitly. `CalculateAsync_RoundsEmployerCostsAwayFromZeroAtAnExactMidpoint` pins it with three genuine midpoints (`100.5 * 0.21 = 21.105`, `125.75 * 0.06 = 7.545`, `50.5 * 0.09 = 4.545`) and asserts both what `AwayFromZero` gives and what `ToEven` would have given, so deleting the argument turns the suite red.

**When an unreachable guard earns its place.** The `catch (OverflowException)` and the `_ => throw new ArgumentOutOfRangeException(...)` arms of the two switches cannot run while the ceiling and `Enum.IsDefined` stand in front of them. A guard like that earns its keeping when (a) it is cheap, (b) the thing that makes it unreachable is a *separate* line that a future edit could move or relax, and (c) it fails loudly rather than silently. All three hold here — which is why the switch arms now carry a message saying so (`"Unreachable: guarded by Enum.IsDefined above."`) instead of a bare `new ArgumentOutOfRangeException()` that tells a debugging colleague nothing. A guard that hides a real case, or that swallows the failure into a default value, is noise and should go.
